## 概要

本版本包含两个 OpenSpec change 的全部实现、若干修复和项目扩展点：
- 后台敏感操作重新验证与 MCP 确认执行（add-admin-step-up，#491、#493、#494、#499）；
- Cloudflare 部署资源解析（add-deploy-autoprovision，#492、#495、#496）；
- 修复与项目扩展点（#497、#498）。

另外补记 0.9.1 已交付、但 0.9.1 说明漏写的 add-ops-safeguards 防护（#485、#486、#488、#489、#490）。其中「插件 cron 的 `safety` 必填」从 0.9.1 起就是不兼容变更。已在 0.9.1 处理过的项目跳过对应动作。

不兼容点：
- 后台写操作必须使用登记过的动作名。项目自加的后台写操作没登记时，类型检查和守卫测试会失败。
- 敏感后台操作已强制要求重新验证（step-up）。项目自有的后台界面直接调用敏感 Server Function 时，管理员只会看到失败。
- MCP `settings.set` 写密钥类设置、`models.update` 改定价，改为返回 `needs_owner_confirm`，由令牌所属管理员在后台确认后才执行。
- 项目自有插件的 cron 必须声明 `safety`（0.9.1 起）。
- 项目自定义的部署工作流要接入资源解析步骤与生成的部署配置。

### 后台敏感操作重新验证（add-admin-step-up）

- **动作登记表**：全部后台写操作的动作名登记在 `apps/web/src/features/admin/actions.registry.ts`。每项声明 `stepUp`，取值为 `'always'`、`'never'`，或按已校验输入判定的函数，并写明理由。
  - 插件用 `defineAdminActions(<插件 ID>, { … })` 追加登记，键重复会报错。
  - `adminAction`、`withAdminAction`、`runAdminAction` 只接受登记过的名字。`withDelegatedAdminAction` / `runDelegatedAdminAction` 新增必填的动作名参数。
  - `actions.registry.scan.test.ts` 检查调用点与登记表双向一致。
- **重新验证**：敏感操作要求当前会话在最近 `admin.stepUpMinutes` 分钟内（默认 10）验证过一次，未验证时返回 403 `STEP_UP_REQUIRED`。
  - 可用方式按账号已有手段取最强者：开启两步验证时为 TOTP / 备用码；否则为邮箱验证码，有密码另加密码。
  - 验证在当前会话内完成，不新建也不替换会话。
  - 失败按 IP 与账号限流，连续失败锁定 15 分钟。
  - 审计事件：`admin.step_up.verified`、`admin.step_up.locked`。
  - 详见 [后台重新验证](../04-auth-and-tenancy.md#后台重新验证step-up)。
- **后台界面**：
  - `useStepUpCall` 收到 `STEP_UP_REQUIRED` 时弹出验证框 `StepUpDialog`（手机端为底部面板），通过后用原参数重试一次。
  - 后台顶部显示「已验证，剩余 N 分钟」，救援开关开启时显示警示条。
  - `@saas/ui` 新增 `InputOTP`，不引入新依赖。
- **救援开关**：可选密钥 `ADMIN_STEP_UP_RESCUE`（`1` / `true`）。开启后，`BOOTSTRAP_ADMIN_EMAILS` 名单内的管理员在丢失两步验证时可用邮箱验证码完成验证，方式记为 `rescue`。
  - 每次救援验证都写审计，并发送新的运营事件 `admin.step_up.rescue`（Telegram / Discord）。
  - 日常保持留空。[后台重新验证应急恢复](../runbooks/admin-step-up-rescue.md)
- **MCP 确认执行**：AI 经 MCP 发起的敏感写入不再直接执行，而是生成待确认记录（有效 30 分钟，每个令牌最多 20 条），返回 `{ status: "needs_owner_confirm", confirmationId, confirmUrl, expiresAt, summary, message }`。
  - 令牌所属管理员在确认页 `/admin/confirm/$id` 重新验证后执行或拒绝。待确认列表在 `/admin/confirmations`，后台导航显示待确认数量。
  - 密钥参数用 AES-GCM 加密暂存，数据密钥存在平台缓存，缓存键前缀为 `admin-confirmation:key:`。记录进入终态时清除密文。
  - 执行审计合并 `via`、`tokenId`、`tool`、`confirmationId`、`confirmedBy`、`stepUpMethod`。新增审计事件：`admin.confirmation.requested`、`admin.confirmation.confirmed`、`admin.confirmation.rejected`。
  - 新增 MCP 工具：
    - `credits.adjust`：增加积分或收回批次；
    - `refunds.review`：审核退款，通过与驳回都要确认；
    - `confirmations.get`：只读，查询确认结果。
  - `settings.set` 只在实际改动密钥类设置时要确认，`models.update` 只在改动定价时要确认。`dryRun: true` 与非敏感写入不变。
  - 每日清理挂在现有 UTC 03:00 触发器上（`admin-confirmations-cleanup`，不新增 cron）：过期的待确认记录标为 `expired`，删除 30 天前的终态记录。该任务已登记在 [批量任务登记表](../bulk-jobs.md)。
  - [需要管理员确认的操作](../admin-mcp.md#需要管理员确认的操作)
- `@saas/billing` 的 `reviewRefundRequest` 新增可选参数 `auditMeta`、`inDecision`，不传时行为不变。后台退款页使用的支付运行时与退款选项移到 `apps/web/src/features/billing/admin-refunds.server.ts`。

### Cloudflare 部署资源解析（add-deploy-autoprovision）

- 新命令 `pnpm deploy:resources --env <staging|production>`（`scripts/deploy/resources.mjs`）。部署前解析 KV、R2 桶、队列（含死信队列）和 Hyperdrive，生成 `apps/web/wrangler.deploy.json` 与 `apps/jobs/wrangler.deploy.json`。这两个文件被 Git 忽略。
  - 已填写真实 ID 的绑定沿用原 ID，不调用 API。
  - 占位 ID 会按约定名称查找。只有 `--apply` 时才创建缺失的 KV、R2 和队列。
  - Hyperdrive 必须显式加 `--create-hyperdrive` 并提供 `HYPERDRIVE_APP_URL`。
  - production 的 apply 另需 `--allow-production`。
- 工作流：staging 在迁移前运行 `pnpm deploy:resources --env staging --apply`，production 在构建前只运行 plan，缺资源时中止。
  - jobs 的构建与部署都改为 `--config wrangler.deploy.json`。
  - web 构建通过 `WRANGLER_DEPLOY_CONFIG` 读取生成的配置。
  - 部署命令关闭 Wrangler 的自动创建资源。
- 生成器按项目名哈希分配限流 `namespace_id` 号段，模板保留 1001–1015。新项目保留 KV / Hyperdrive 的占位 ID。`PROJECT_SETUP.md` 的资源段分为「自动解析」和「需要提供」两部分。
- 详见 [部署资源自动解析](../07-infrastructure.md#部署资源自动解析cloudflare) 与 [创建项目](../create-project.md)。

### 运维防护（add-ops-safeguards，0.9.1 已交付，此处补记）

- **定时删除与群发防护**（#490）：
  - 每轮上限：以下任务改为每轮最多处理固定数量，超出部分留到下一轮，最早到期的先处理。
    - 文件清理：500 个对象 / 20 个空间；
    - 删号凭据清单：200；
    - 个人空间分享卡：20 个空间；
    - 过期空间清理：20 个空间；
    - 积分过期：200 个空间；
    - 预扣结算：500；
    - PayPal 到期取消：50 次；
    - 退款联系邮箱清理：500。
  - 时间防护：删除类任务以数据库时钟为准。下列情况整轮不执行：应用与数据库时钟偏差超过 5 分钟、截止时间异常、保留期异常。
    - 时间列早于 `2024-01-01T00:00:00Z` 或在未来的行不再删除，只计数并告警，需要人工处理。
  - 运营事件：新增 `ops.bulk_job.guard_tripped`，同一任务同一原因每个 UTC 日最多发一条。
  - 对账告警：对账失败告警改为每轮最多 10 条明细加 1 条汇总，当天重跑不重复发送。
  - agents 的保留期检查改用数据库时钟。
  - 登记要求：插件 cron 的 `safety` 改为必填（`apps/jobs/src/plugins/module.ts` 的 `PluginCronTask`）。删除、销毁积分、外部写入和群发任务须登记在 [批量任务登记表](../bulk-jobs.md)。不是 cron 触发的入口（如 Durable Object alarm）同时加入 `apps/jobs/src/bulk-job-registry.ts` 的 `NON_CRON_BULK_JOBS`。
- **R2 / KV 临时错误重试**（#489）：写入与删除遇到临时错误时有限次重试。
  - 重试耗尽时，R2 返回 `STORAGE_UNAVAILABLE`（503），KV 返回 `CACHE_UNAVAILABLE`（503），错误中不含原始错误与对象键。
  - 调用方不要再自己包一层重试。[存储与缓存的临时错误重试](../platform-capabilities.md#存储与缓存的临时错误重试)
- **公开页面优先**（#488）：
  - 环境校验失败时，Worker 仍先返回命中的预渲染页。
  - 插件绑定不再参与全站校验：某个插件缺绑定时，只有该插件的入口返回 503，`/api/health` 的 `plugins` 字段列出各插件状态。
  - 新插件入口须用 `pluginUnavailable(runtime, '<id>')` 自行检查。[插件开发与部署](../plugins.md)
- **第三方登记**（#486）：`pnpm check` 新增 `scripts/check-third-party.mjs`。受监视的第三方 SDK 依赖必须在 `scripts/third-party-deps.json` 中映射到 [第三方登记表](../third-party.md) 的一行。
- **MCP 工具参数说明**（#485）：`defineAdminTool` 的 `params` 必须为每个输入参数写说明，无参数的工具写 `params: {}`。守卫测试会校验 [工具表](../admin-mcp.md#工具与权限) 与实现一致。

### 修复与项目扩展点

- **同分支续同步**（#497）：已完成同步的衍生项目可以指定原来的 `--branch`，在同一分支上继续同步到更新的模板目标。工具会核对同步记录和分支历史，拒绝包含无关提交的分支，也拒绝等于或早于记录的目标。
- **令牌页入口包**（#497）：后台 API 令牌页移除路由专属的加载骨架（`pendingComponent`），避免它随公共路由树进入首页的水合闭包。后台布局统一显示加载提示，令牌页保留设计稿的空态、失败提示和重试按钮。
- **公开页面优先的项目扩展点**（#498）：0.9.1 起，Worker 在环境校验失败时也会先返回命中的预渲染静态资源。这一步早于所有闸门，会绕过衍生项目写在 `server.ts` 里的站点规则，例如：
  - 多站点按 Host 选预渲染目录；
  - 非本站语言前缀返回 404，默认语言前缀 301；
  - 静态页 CSP 与站点 favicon。

  本版本把这些规则移到项目自有文件，template-sync 更新 `server.ts` 与 `__root.tsx` 时不再与项目改动冲突。没有改过这两个文件的项目行为不变。[项目自有扩展文件](../02-project-structure.md#项目自有扩展文件)
  - 新增项目自有文件 `apps/web/src/server/project-gate.ts`，首次交付后 template-sync 不覆盖。
    - `gateProjectRequest(request, { env, envValid })` 在查找预渲染静态资源之前调用，环境校验失败时同样先调用。
    - 返回 `Response`：直接响应，并按静态响应补安全头，HTML 按内联脚本哈希补 CSP。
    - 返回 `Request`：作为查找静态资源的改写请求；未命中时，动态流程仍用原始请求。
    - 返回 `undefined`：不处理（模板默认）。
  - 同一文件的 `staticFirst` 默认为 `true`。设为 `false` 时恢复 0.9.0 行为：环境校验失败时静态页也返回 500。插件 `worker.fetch` 仍在静态资源之后。
  - 新增项目自有文件 `apps/web/src/features/app-shell/root-fallbacks.project.tsx`，导出 `RootNotFound`、`RootError`，默认就是模板的 `NotFoundPage` / `ErrorPage`。`__root.tsx` 的 404 / 错误组件和 `router.tsx` 的默认组件都从这里取，分享页的错误界面也随之使用项目组件。
  - template-sync 的 `projectOwnedPaths` 补登 `apps/web/src/features/app-shell/nav.project.ts`（此前只在发版检查中登记），同步不再覆盖项目的导航登记。

### 已有项目如何把自有闸门迁到钩子

适用于在 `apps/web/src/server.ts` 里自行加了站点 / 语言闸门，或在 `routes/__root.tsx` 里换了 404 / 错误组件的项目。

1. 同步时 `server.ts` 的冲突以模板版本为准解决，再把「静态资源之前」的规则搬进 `project-gate.ts` 的 `gateProjectRequest`：
   - 站点闸门的拒绝、重定向（如默认语言前缀 301）、本站风格的 404：返回 `Response`；
   - 按 Host 选预渲染目录：返回改写路径后的 `new Request(url, request)`，由模板查 `ASSETS`；
   - 站点 favicon：对 `/favicon.ico` 返回改写后的请求，或直接返回 `env.ASSETS.fetch` 的结果。

   静态页的 CSP 补头由模板统一处理（钩子返回的响应和命中的静态资源都经过 `withStaticSecurityHeaders`），删掉项目自己的补头代码。
2. 只和动态请求有关的闸门（公开 API、后台、语言 Cookie 等）继续用模板入口已有的闸门或插件 `worker.fetch`。钩子运行在环境校验与运行时之前，不要在里面查库或读会话。
3. 暂时不能迁移、又必须保证闸门先于静态页时，先在 `project-gate.ts` 设 `staticFirst = false`：环境校验失败时公开页也返回 500，校验通过时行为同 0.9.0。迁移完成后改回 `true`。
4. `__root.tsx` 的冲突以模板版本为准解决，把项目品牌的 404 / 错误组件放到 `root-fallbacks.project.tsx`，导出为 `RootNotFound` / `RootError`。根路由出错时模板仍会补上 HTML 外壳（`RootDocument`），项目组件只渲染页面主体。

## 必须执行的动作

1. 登记项目自有的后台写操作：项目在 `apps/web` 或自有插件里调用 `adminAction`、`withAdminAction`、`runAdminAction`、`withDelegatedAdminAction`、`runDelegatedAdminAction` 的地方，都要使用登记过的动作名。
   - 模板已有的动作直接沿用。项目新增的动作：插件用 `defineAdminActions('<插件 ID>', { '<动作名>': { stepUp, reason } })` 追加；`apps/web` 内的动作加到 `actions.registry.ts`。
   - `stepUp` 的取值：会动钱、积分、密钥、权限或能冒充用户的，用 `'always'` 或输入判定函数；其余用 `'never'`。
   - `withDelegatedAdminAction` / `runDelegatedAdminAction` 补上新增的动作名参数。
   - 完成后 `pnpm typecheck` 应通过，`apps/web` 的 `actions.registry.scan.test.ts` 应通过。没有自有后台写操作的项目由三方合并自动完成。
2. 项目自有的后台界面改用 `useStepUpCall` 调用敏感写操作：
   - 写法：`const call = useStepUpCall(serverFn, { action: '<操作名>' })`，从 `apps/web/src/features/admin/step-up/step-up-provider.tsx` 导入。用户取消验证时返回 `STEP_UP_CANCELLED`，用 `isStepUpCancelled` 判断，表单保持原样。
   - 服务端把业务错误包成 `{ ok: false, error }` 返回的入口，要在 catch 里先调用 `rethrowStepUpRequired(error)`，否则浏览器收不到 `STEP_UP_REQUIRED`。
   - 项目 e2e 若执行敏感后台操作，用 `e2e/fixtures.ts` 的 `grantStepUp(sql, userId)` 预置验证状态。
   `STEP_UP_ENFORCED` 开关与 `overrideStepUpEnforcedForTesting` 已删除，引用它们的项目代码要一并删除。
3. 改造依赖 MCP 即时写入的脚本或 agent：
   - `settings.set` 写密钥类设置、`models.update` 改定价，现在返回 `needs_owner_confirm`。这是普通结果，不是错误。
   - 收到后把 `confirmUrl` 交给令牌所属管理员确认，再用只读工具 `confirmations.get` 查询结果。
   - 别的管理员不能确认，只能拒绝。令牌吊销或过期后，记录不能再被确认。
   - 处理建议见 [需要管理员确认的操作](../admin-mcp.md#需要管理员确认的操作)。
   - 项目自有 MCP 工具若调用登记为敏感的后台动作，要实现 `defineAdminTool` 新增的 `confirm(ctx, args)` 与 `execute(ctx, payload)`，否则调用会以 `STEP_UP_REQUIRED` 被拒（MCP 没有会话，不能绕过重新验证）。停用 `admin-mcp` 的项目跳过本条。
4. 平台管理员准备重新验证手段：
   - 建议开启两步验证并保存备用码；开启后，密码和邮箱验证码都不再可用。
   - 未开启两步验证的管理员，需要已验证邮箱（用邮箱验证码），或有密码（用密码）。只能用 OAuth 登录、邮箱又未验证的管理员没有可用方式，要先验证邮箱。
   - 引导管理员的邮箱应写在 `BOOTSTRAP_ADMIN_EMAILS` 里，以便必要时用救援开关恢复。
5. 项目自有插件声明了 `crons` 时，为每个任务补必填的 `safety`（0.9.1 起，已处理的项目跳过）。
   - 只读、或只写自身状态的任务：`safety: { kind: 'none', reason: '<为什么不涉及删除或发送>' }`。
   - 会删除数据、销毁积分、调用外部写或批量发送的任务：`safety: { kind: 'delete' | 'destroy-credit' | 'external-write' | 'send', cap, capUnit, order, timeGuard }`，在 `docs/bulk-jobs.md` 登记表加一行，并让 `run` 返回 `{ guard }`（`@saas/shared/bulk-job` 的 `checkBulkJobTime` / `bulkJobOutcome`）。
   - 项目自行新增、不经插件 cron 的删除 / 群发任务同样要登记，否则 `apps/jobs/test/bulk-jobs.guard.unit.test.ts` 失败。
   模板内置插件都没有 `crons`。
6. 项目自有的 MCP 工具（`defineAdminTool`）为每个输入参数在 `params` 中写英文说明，无参数的工具写 `params: {}`，并同步更新项目文档中的工具表（0.9.1 起，已处理的项目跳过；停用 `admin-mcp` 的项目跳过）。
7. 新增受监视的第三方 SDK 依赖时，同时在 `scripts/third-party-deps.json` 加映射、在 `docs/third-party.md` 加登记行；`pnpm check` 会拦截未登记的依赖（0.9.1 起）。
8. 合并部署工作流与 Vite 配置：
   - 没有自定义 `.github/workflows/deploy-staging.yml`、`deploy-production.yml` 与 `apps/web/vite.config.ts` 的项目，由三方合并自动完成。
   - 自定义过的项目按「配置变更」中的部署工作流一项手动接入。
   - **不要删除 `wrangler.jsonc` 中已填的 KV 或 Hyperdrive ID**：清空后会改为按名称查找，允许创建时可能绑定到一组空资源。
   - 同步分支若带入生成器的新限流号段，保留现用的 `namespace_id`，可以延续已有计数。
   （适用：target=cloudflare）
9. 按 GitHub environment 调整 `CLOUDFLARE_API_TOKEN` 的权限。只有存在占位 ID 或需要自动创建资源的环境才必须调整；KV、Hyperdrive ID 都已固定的环境，解析步骤不调用 API，可以跳过。
   - staging：`Workers KV Storage Write`、`Workers R2 Storage Write`、`Queues Write`、`Hyperdrive Read`；
   - production：只读的 `Workers KV Storage Read`、`Workers R2 Storage Read`、`Queues Read`、`Hyperdrive Read`；
   - Worker 发布步骤照常需要发布权限。
   （适用：target=cloudflare）
10. 自定义过项目闸门的多站点 / 多语言项目，按上文「已有项目如何把自有闸门迁到钩子」迁移；在 `__root.tsx` 换过 404 / 错误组件的项目，把组件移到 `root-fallbacks.project.tsx`。（适用：target=cloudflare）
11. 同步后运行 `pnpm install`、`pnpm --filter @saas/db db:migrate`（本地），再运行 `pnpm check`、`pnpm typecheck`、`pnpm test`、`pnpm build`；selfhost 项目另运行 `pnpm build:node`。

## 部署顺序

1. 完成「必须执行的动作」1–2、5–7，`pnpm check`、`pnpm typecheck` 通过后再继续。重新验证在新代码上线后立即生效，上线前确认管理员已具备可用的验证方式（动作 4）。
2. Cloudflare 项目先完成动作 8、9：同步资源解析脚本，以及引用部署配置的工作流与 Vite 配置。
   - 已固定资源 ID 的项目，默认解析无需调用资源 API。
   - 新项目或依赖自动解析的环境，先在项目根目录运行 `pnpm deploy:resources --env staging`，核对名称、归属和缺项。
   - 需要 Hyperdrive 时，按计划准备好数据库 app 账号的连接串。维护者可在本地用 `--apply --create-hyperdrive` 和 `HYPERDRIVE_APP_URL` 创建。[Hyperdrive 官方指南](https://developers.cloudflare.com/hyperdrive/get-started/)（2026-11-26 核对）
3. 应用数据库迁移 `0027_admin_step_up`。这是扩展迁移，可以在旧代码运行时先执行。
4. 按原顺序先部署 jobs、再部署 web；模板 CI 的顺序是资源解析 → 迁移 → jobs → web。
   - staging 流水线运行 apply，补齐缺失的 KV、R2 桶和队列。
   - production 流水线只运行 plan，资源缺失时中止。需要补齐生产资源时，由维护者在本地核对计划后运行 `pnpm deploy:resources --env production --apply --allow-production`。
5. selfhost：用包含本版本代码的同一 SHA 镜像发布，`deploy.sh` 会先迁移再切换服务。资源解析只用于 Cloudflare。

不需要 `requiresDeployed`。

部署后：
- 资源解析：已有环境核对计划输出中的固定 ID 和资源名称与原配置一致；新环境核对 plan 所列缺项与 apply 摘要中的新增资源。staging 发布后确认健康检查返回目标提交的完整 SHA，并通过 staging 冒烟。
- 重新验证：
  - 管理员在后台执行一次可逆的敏感操作（例如给测试空间加积分再收回），应弹出验证框；用本账号可用的方式通过后，操作自动继续。
  - `/admin/audit` 中能看到 `admin.step_up.verified`。
  - 换一个浏览器（新会话）再做敏感操作，应再次要求验证。
- MCP 确认：
  - 用管理员令牌调用 `credits.adjust` 给测试空间加积分，应返回 `needs_owner_confirm`。
  - 打开 `confirmUrl` 确认后，`confirmations.get` 返回 `done`。
  - 再发起一条后拒绝，`confirmations.get` 返回 `rejected`。
- 公开页面与扩展点：
  - 首页、定价、博客、法律页返回 200。
  - `/api/health` 的 `plugins` 字段显示各插件状态。
  - 迁移了闸门的多站点项目，用两个站点的 Host 请求同一预渲染路径，确认返回各自站点的页面；请求非本站语言前缀与默认语言前缀，确认 404 与 301。
  - 在暂时缺一项必填密钥的预览环境中，预渲染页仍返回 200（`staticFirst = false` 时为 500）。
- 同步：在衍生项目已有的同步分支上，用目标版本的同步脚本指定原 `--branch` 和更高的 `--to`，确认成功后基准记录指向新目标。分支上已有无关提交时，另开同步分支。
- 运营：上线后一周关注 jobs 日志中的 `job.cap_reached`、`job.guard_tripped`，以及运营通知渠道。
