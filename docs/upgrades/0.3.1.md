## 概要

- 新增夜间 CI，定期运行离线全量 e2e 与生成项目验证，失败时保留报告并自动通知。
- 修复对话消息顺序：同一轮里回复可能排在提问之前，现在读取时统一按提问在前的稳定顺序排序。
- **反馈共享对话同意（add-subject-chat 10）**：用户点踩提交反馈时可勾选「共享这条回复及之前几条消息，用于改进回答」（默认不勾选，每条反馈单独同意，可撤回）；只有同意的反馈，后台 `/admin/feedback` 才能查看被评回复与它之前最近 3 条消息，每次查看写审计。

### 对话消息顺序修复

新写入的每轮对话先生成用户消息 ID，再生成助手消息 ID，确保 UUIDv7 的顺序与提问、回复顺序一致。
已有数据的回复 ID 可能早于提问 ID，且同一事务中的 `created_at` 相同，因此读取时统一按
`(created_at, role 为 user 的排在前, id)` 排序，无需迁移或重写已有数据。

衍生项目如果自行实现了消息读取（如对话页、模型 history、导出或后台查看），需要改用
`@saas/ai` 导出的 `aiMessageOrder`，替换仅按 ID 或创建时间排序的逻辑：

```ts
import { aiMessageOrder } from '@saas/ai'

// 在已有租户与对话过滤之后应用排序
query.orderBy(...aiMessageOrder())
```

需要从最新消息开始读取时使用 `aiMessageOrder('desc')`，它反转全部排序项。
查找某条回复对应的提问也不能继续用 `user.id < assistant.id`；同一时间的用户消息应先于回复。

## 配置变更

### 夜间全量测试

新增 `.github/workflows/nightly.yml`（Actions 中的 **Nightly**），每日 UTC 19:00（北京时间次日 03:00）定时运行，支持 `workflow_dispatch`；仅运行 `main`。衍生项目同步模板后会继承此 workflow，可按需删除文件或修改 `schedule`。

- `e2e-full` 使用临时 Postgres 17，执行 `pnpm --filter @saas/web test:e2e`，采用默认 `playwright.config.ts`，不需要外部服务密钥；不包含 Stripe 专用测试、staging / production 项目及 `ai-chat-disconnect`。
- `create-project-verify` 独立执行 `pnpm test:create-project:verify`；衍生项目不包含该模板维护脚本，自动省略此步骤。
- 失败时上传 Playwright report 与 trace，保留 14 天；自动创建带 `nightly-failure` 标签的 issue，已有未关闭同标签 issue 时追加评论，正文包含日期、失败 job 与 run 链接。

### 反馈共享对话

- 文案文件 `apps/web/messages/<locale>/ai-subject-chat.json` 新增 `subject_chat_feedback_share`、`subject_chat_feedback_share_description` 与若干 `admin_feedback_*` 键，并修改 `admin_feedback_description`；项目新增语言时补齐翻译。
- 隐私说明：启用 AI 对话的项目上线前应在隐私政策中说明这项共享——用户可以在反馈时选择把被评回复和它之前最多 3 条消息共享给平台管理员用于改进回答，不包括关联对象的上下文；同意逐条记录、可随时撤回；说明这些内容的保留期限（随对话删除、删号与删空间清理一并删除）。模板不修改法律页正文。

## 数据库变更

### 0024_feedback_share

- 类别：扩展
- 兼容上一版本代码：是
- 锁表与耗时：`ai_message_feedback` 新增 `share_conversation boolean not null default false`（常量默认值，PostgreSQL 11+ 为元数据变更，不改写表）、可空列 `shared_at timestamptz`，以及 check 约束 `ai_message_feedback_shared_at_consistent`（`share_conversation is distinct from (shared_at is null)`，即两者一致，未带 NOT VALID，持 ACCESS EXCLUSIVE 扫描一次全表；已有行恒为 false 与 NULL、表通常很小，校验瞬时完成）。迁移设置 `lock_timeout=5s`、`statement_timeout=30s`，拿不到锁时失败，可重试
- 回滚：只回退代码，保留新列与约束；旧代码不读写这两列（插入时取默认值 false 与 NULL，满足约束），新代码写入的同意保留

数据迁移：无，已有反馈一律视为未同意，后台不显示其对话正文。

接口变化：`apps/web` 的 `MessageFeedbackValue` 新增可选字段 `shareConversation`（缺省视为 false，服务端返回值总是带上）；`@saas/ui` 的 `MessageFeedback` 新增可选属性 `shareLabels: { label; description }`（不传时不显示勾选项，行为与此前一致），`MessageFeedbackValue` 新增可选字段 `shareConversation`。后台可见范围由 `apps/web/src/features/ai/feedback.ts` 的 `FEEDBACK_SHARED_PRIOR_MESSAGES`（3）控制，修改时同步隐私政策与勾选项说明文案。

## 部署顺序

先执行迁移，再部署 web（新代码读写 `share_conversation` 与 `shared_at`）；jobs 不涉及。

## 验证

- 合并后在 **Actions → Nightly** 手动触发并检查两个 job 的结果；失败时查看报告与 trace，区分过时断言和真实缺陷，修正对应问题，不删除有效用例或增加 retry 掩盖失败。
- 重新打开包含旧消息的对话，确认提问在对应回复之前；继续发送消息，确认模型收到的历史顺序一致。
- 反馈共享：在对话页对一条回复点踩，展开的表单中「共享这条回复及之前几条消息，用于改进回答」默认未勾选；勾选后提交，刷新页面并点「修改反馈」，勾选仍在。
  平台管理员打开 `/admin/feedback`：该条显示「已共享」与「查看对话」，打开后看到被评回复与之前的提问，审计日志新增 `ai.feedback.view_conversation`（只含反馈 ID、空间、消息 ID 与条数）。
  回到对话页取消勾选并重新提交：后台该条显示「未共享」，再请求对话正文返回不存在。

## 回滚

- 夜间测试：删除 `.github/workflows/nightly.yml` 或回退该文件的变更。
- 消息顺序：回退代码即可，无数据库变更。
- 反馈共享（0024）：回退代码；保留新增列与约束即可，不需要回退数据库结构。回退到旧代码期间，旧代码保存反馈的 upsert 不写 `share_conversation` 与 `shared_at`，因此不会清除已有的同意：用户在此期间重新提交反馈不会撤回共享，重新部署新代码后再次提交才会按勾选状态写入。
