# 06 · AI：文本、图片、视频

## 1. 总体设计

| 类型 | 执行方式 | 可选计费方式（按模型配置，见 §2） | 状态存储 |
|---|---|---|---|
| 文本 | 请求内流式（`streamText`），可带工具调用 | 按对话轮次 / 按 token | `ai_conversation` / `ai_message` |
| 图片 | 异步任务（Workflow） | 按生成次数 / 按张数（可按分辨率、步数加权） | `ai_task` + `file` |
| 视频 | 异步任务（Workflow + 服务商回调） | 按生成次数 / 按秒数（可按分辨率加权） | `ai_task` + `file` |

统一原则：
1. **先检查、再预扣、后调用**：权益（模型是否可用、并发数）→ 限流 → `credits.hold()` → 调用模型。
2. **产出落 R2**：服务商返回的 URL 会过期，结果一律转存 R2 并写 `file` 表。
3. **失败必退**：任何失败路径都要 `release`；未结算的 hold 由 Cron 兜底（按类型区分处理，见 05-billing「超时回收」）。
4. **所有 LLM 调用经 AI Gateway**：统一日志、缓存、重试、按服务商的成本统计。

## 2. 模型注册表

`ai_model` 表（后台可编辑，KV 缓存）决定：模型对哪些套餐可见、走哪个 provider、如何计价、接受哪些参数。

### 计费方式

积分消耗支持三种计费方式，**按模型**在 `ai_model.pricing` 中选择——同一个站点可以让聊天按 token、视频按次，具体由站点的产品形态决定：

| 方式 | 适用 | 示例 | 预扣 | 结算 |
|---|---|---|---|---|
| `per_call` 按次 | 对话轮次、生成次数；价格对用户最直观 | 一轮对话 1 分；生成一个视频 5 分，1080p ×2 | 固定值 | 等于预扣，**不会超出** |
| `token` 按 token | 文本，成本随上下文和输出长度变化大 | 输入 2 分/1k，输出 8 分/1k | 估算上限 | 按实际 usage |
| `per_unit` 按用量单位 | 图片张数、视频秒数 | 每张 10 分；每秒 20 分 | 按请求参数计算 | 按服务商回报的 usage |

```ts
type Multipliers = Record<string, Record<string, number>>   // 参数名 → 取值 → 倍率，如 { resolution: { '720p': 1, '1080p': 2 } }

type Pricing =
  | {
      mode: 'per_call'
      credits: number                      // 每轮对话 / 每次生成的积分
      multipliers?: Multipliers            // 按请求参数加权，多个参数相乘
      chargeOn?: 'success' | 'any_output'  // 何时计费：媒体默认 success；文本默认 any_output（中断但已有输出也计费）
      limits?: { maxInputTokens?: number; maxOutputTokens?: number }  // 文本按轮计费时限制单轮成本上限
    }
  | { mode: 'token'; inputPer1k: number; outputPer1k: number; minCharge?: number }
  | { mode: 'per_unit'; unit: 'image' | 'second'; perUnit: number; multipliers?: Multipliers }

function estimateCredits(pricing, input): number   // 预扣用：per_call 为固定值，其余取上限
function actualCredits(pricing, usage): number     // 结算用：per_call 直接返回预扣值
```

- **按次计费的成本控制**：文本按轮计费时，平台的实际成本仍随上下文长度增长，必须配 `limits`（截断历史到 `maxInputTokens`、限制 `maxOutputTokens`），否则长会话会让单轮成本无上限。
- **默认值**：新建模型时的默认计费方式取 `template.config.ts` 的 `ai.defaultPricingMode`（如文本 `token`、图片和视频 `per_call`），后台可以逐个模型修改。
- **展示**：模型选择器与生成按钮旁显示本次预计消耗（按次直接显示固定值；按 token 显示「约 X–Y 分」）；用量页每条流水注明计费方式。

**定价快照**：`ai_model` 经 KV 缓存，后台改价后各地生效有延迟。为保证同一次调用的预扣与结算口径一致，发起调用时把当时的 `pricing` 写入 `ai_message.pricing` / `ai_task.pricing`，`estimateCredits` 与 `actualCredits` 都只读这份快照，不再重新读取 `ai_model`。改价只影响之后发起的调用。

`params_schema`（JSON Schema）用于：前端动态渲染参数表单、服务端校验输入，二者一致。

## 3. 文本

### 实现
- `packages/ai/text`：根据 `ai_model.provider` 返回 AI SDK 的 model 实例，baseURL 指向 AI Gateway：
  - OpenAI、Anthropic、Google 等官方 provider（AI Gateway 提供各家兼容端点）
  - 也可接入 Workers AI（`AI` 绑定）或 OpenRouter 作为补充
- 接口：`POST /api/ai/chat`，使用 AI SDK 的 UI message 流协议；前端 `useChat`。

### 流程
```
1. 解析会话、校验模型可用；取定价快照 pricing
2. 计算预扣额与 maxOut：
   per_call：amount = credits × multipliers；按 limits 截断历史，maxOut = limits.maxOutputTokens ?? 模型上限
   token：   inputCost = inputTokens(保守估算，宁高勿低) * inputPrice
             maxOut = min(模型/请求的 maxOutputTokens, floor((balance - inputCost) / outputPrice))
             若 maxOut < minOutputTokens（如 256）→ INSUFFICIENT_CREDITS
             amount = inputCost + maxOut * outputPrice
3. hold(amount)                                     // expires_at = now + 10min
   插入 assistant message（status='streaming', hold_id）
4. result = streamText({ model, messages, maxOutputTokens: maxOut, tools?, abortSignal })
5. ctx.waitUntil(result.consumeStream())           // 服务端独立读完模型流，与客户端连接解耦
6. onFinish({ usage }) → capture(actualCredits(pricing, usage)) → message.status='completed'
   onError → token：按已产生 usage 结算（拿不到则按最低费用）
             per_call：有输出且 chargeOn='any_output' → capture 全额，否则 release
             → message.status='failed'
```

- **按余额压低 `maxOutputTokens`**（仅 token 计费）：按模型上限全额预扣，会让余额不多的用户连短对话都发不出去；改为按余额计算本次可用的最大输出，余额只够很短的回复时才拒绝。
- **输入 token 保守估算**：token 计费时，超出预扣的唯一来源是输入 token 估算偏低（输出已被 `maxOutputTokens` 硬性限制），因此估算宁高勿低（如按字符数的保守系数，或调用服务商的 token 计数接口），把超出控制在 05-billing「超额容忍」的额度内。
- **客户端中断不影响结算**（已实测，见下方「实测记录」）：Workers 中客户端断开后，请求上下文随即被取消，不在 `waitUntil` 中的读取在断开时就停止，挂在响应流上的 `onFinish` 不会执行。第 5 步用 `consumeStream()` 在服务端把模型流读完并放进 `waitUntil`，用户关闭页面后服务端仍继续读流，只要模型在**断开后 30 秒内**输出完毕，`onFinish` 就会以完整 usage 触发并写库（代价是被中断的回复仍按完整输出计费，与上游实际计费一致）。客户端保持连接期间不受这个时限约束（流持续多久都可以）。若希望用户点「停止」时同时停止上游生成，则前端调用显式的 stop 接口，服务端 abort 后按已产生 usage 结算，`message.status='aborted'`。
- **兜底**：`waitUntil` 的时限是**客户端断开（或响应结束）后 30 秒**（实测，与官方文档一致）。超时后运行时直接取消剩余任务（日志：`waitUntil() tasks did not complete within the allowed time after invocation end and have been cancelled`），`onFinish` / `onError` / `catch` / `finally` 都不会执行，因此断开时剩余输出超过 30 秒的回复会丢失结算。此时 hold 在 10 分钟后由 Cron 按最低费用 capture（见 05-billing「超时回收」），而不是全额退回。
  - 建议（未实现，留给 AI change 决定）：在断开时（`request.signal` 的 `abort` 事件）启动一个约 25 秒的计时器，到期仍未结束就主动 abort 模型流，让 `onAbort` / `onError` 在时限内按已产生的 usage 结算；或在流式过程中定期把累计 usage 写入 `ai_message`，让 Cron 兜底按已记录的 usage 而不是最低费用 capture。需要超长输出（数分钟）的模型，可改由 Durable Object 承载生成过程，不受请求的 `waitUntil` 时限约束。
  - 观测注意：客户端断开的请求在 Workers Logs / `wrangler tail` 中的 `outcome` 为 `canceled`，即使 `waitUntil` 中的结算已成功完成；判断是否结算要看 `ai_message.status`，不能看请求的 `outcome`。

> **实测记录（tasks 7.3，2026-10-03，wrangler 4.146，compatibility_date 2026-10-01）**：临时 Worker 产生每 500 ms 一块的模拟模型流，`tee()` 一路作为响应、另一路在 `ctx.waitUntil` 中读完，读流期间每 5 秒、读完时各写一行 `setting`（经阶段一 staging 的 Hyperdrive）；客户端在约 6 秒时主动断开。代码与复现步骤见 `scripts/probes/stream-7_3/`。
>
> | 场景 | 断开（或响应结束）后源流还需 | 服务端读到 / 应有块数 | 读完并写库 | 最后一次写库（距请求开始） |
> |---|---|---|---|---|
> | 不断开（基线） | — | 40 / 40 | 是 | 20 s |
> | `waitUntil`，断开 | 约 9 s | 30 / 30 | 是（2 次） | 15.2 s、15.3 s |
> | `waitUntil`，断开 | 约 29 s | 70 / 70 | 是（2 次） | 35.8 s、36.0 s |
> | `waitUntil`，断开 | 约 59 s / 119 s / 299 s | 71 / 130、71 / 250、71 / 610 | 否（4 次均在断开后约 30 s 被取消） | 36.3–36.6 s |
> | 不用 `waitUntil`（对照），断开 | 约 29 s | 11 / 70 | 否（断开即停止） | 5.5 s |
> | 立即返回短响应，只在 `waitUntil` 中读流 | 10 s / 30 s | 全部 | 是 | 10 s、30 s |
> | 同上 | 60 s / 120 s | 47 / 120、51 / 240 | 否（响应结束后约 30 s 被取消，请求 wallTime 约 30.5 s） | 26 s、25.5 s |
>
> 结论：`waitUntil(consumeStream())` 能让断开后的读流与写库继续进行，时限为断开或响应结束后 30 秒，超过即被静默取消。
- 实际消耗超过预扣时，**不中断生成**，输出完成后按 05-billing「超额容忍」结算：额度内由平台承担，超出额度的部分从余额补扣，余额不足记为欠费。
- 上下文管理：按模型 context window 截断历史；长会话可做摘要（后续）。
- 工具调用、RAG：作为扩展点（`tools` 注册表），模板首版只提供示例工具。

## 4. 图片 / 视频：异步任务

### MediaProvider 接口

```ts
export interface MediaProvider {
  id: 'fal' | 'replicate' | 'workers-ai' | string
  capabilities: {
    idempotentSubmit: boolean   // 服务商是否支持幂等键去重提交
  }

  submit(input: {
    modelId: string
    params: Record<string, unknown>
    webhookUrl?: string
    idempotencyKey: string     // = ai_task.provider_request_key；不支持时实现方忽略
  }): Promise<{ jobId: string; sync?: MediaResult }>   // 同步返回的模型直接给结果

  getStatus(jobId: string): Promise<
    | { status: 'queued' | 'running'; progress?: number }
    | { status: 'succeeded'; result: MediaResult }
    | { status: 'failed'; error: { code: string; message: string } }
  >

  parseWebhook(req: Request, rawBody: string): Promise<{ jobId: string; result?: MediaResult; error?: ... }>
  cancel?(jobId: string): Promise<void>
}

type MediaResult = {
  outputs: { url: string; mime: string; width?: number; height?: number; durationSec?: number }[]
  usage?: { images?: number; seconds?: number }
}
```

首个实现：**fal.ai**（队列 API + webhook，覆盖大量图片与视频模型）。之后可加 Replicate、Workers AI、各厂商直连 API。

### 任务生命周期

```
queued ──► running ──► succeeded
   │           │
   └──► canceled   └──► failed
```

### Workflow（`apps/jobs/src/workflows/ai-media.ts`，示意）

```ts
export class AiMediaWorkflow extends WorkflowEntrypoint<Env, { taskId: string }> {
  async run(event, step) {
    const task = await step.do('load', () => loadTask(event.payload.taskId))

    // 提交与记录 jobId 在同一个 step 内完成；重试只针对「确定未被受理」的错误
    const { jobId, sync } = await step.do('submit', { retries: { limit: 3, delay: '10 seconds', backoff: 'exponential' } },
      () => submitOnce(task))

    let result = sync
    if (!result) {
      // 回调可能早于 waitForEvent 到达：先查回调入口落库的结果
      result = await step.do('check-callback', () => readCallbackPayload(task.id))
    }
    if (!result) {
      // 等待服务商回调；超时后改为主动轮询
      const ev = await step.waitForEvent('provider-callback', { type: 'media.done', timeout: '15 minutes' }).catch(() => null)
      result = ev?.payload
        ?? await step.do('recheck-callback', () => readCallbackPayload(task.id))
        ?? await pollUntilDone(step, jobId, task.deadline_at)   // 每次轮询是一个 step + step.sleep；超过 deadline 视为失败
    }

    if (result.failed) {
      await step.do('fail', () => failTaskAndRelease(task.id, result.error))
      return
    }
    const files = await step.do('persist', () => copyOutputsToR2(task, result.outputs))
    await step.do('settle', () => succeedTaskAndCapture(task.id, files, actualCredits(task.pricing, result.usage)))
    await step.do('notify', () => enqueueNotification(task))
  }
}

async function submitOnce(task) {
  // 1. 上一次尝试已拿到 jobId（step 内写库成功但返回前失败）→ 直接复用，不再提交
  const fresh = await loadTask(task.id)
  if (fresh.provider_job_id) return { jobId: fresh.provider_job_id }

  try {
    const r = await provider.submit({ modelId, params, webhookUrl: callbackUrl(task.id),
                                      idempotencyKey: task.provider_request_key })
    // 2. 拿到 jobId 立即落库并置 running（与提交放在同一 step，缩小与回调的竞争窗口）
    await markRunning(task.id, r.jobId)
    return r
  } catch (e) {
    // 3. 服务商不支持幂等键时，超时 / 连接中断 / 5xx 属于「可能已受理」，重试会造成重复提交和重复扣费：
    //    不重试，直接让任务失败并退款（用 NonRetryableError 跳过 step 的重试）
    if (!provider.capabilities.idempotentSubmit && isAmbiguous(e)) throw new NonRetryableError(...)
    throw e   // 4xx 校验错误、明确的限流拒绝等「确定未受理」的错误：正常走 step 重试
  }
}
```

- **提交幂等**：`ai_task.provider_request_key` 在创建任务时生成（如 `task.id`）。支持幂等键的服务商可以安全重试任何错误；不支持的只重试「确定未受理」的错误，不确定的情况宁可失败退款，也不重复提交。
- **转存 R2**：`R2.put` 接收 `ReadableStream` 时要求已知长度。服务商响应带 `Content-Length` 时，经 `FixedLengthStream` 直接流式写入（先校验长度不超过上限）；没有 `Content-Length`（如 chunked 响应）时改走 R2 multipart upload 分片写入（除最后一片外每片 ≥ 5MB，累计超过上限即中止），避免把整个视频读进 128MB 内存。

> Workflows 的 `waitForEvent` / `sendEvent` API 细节以实现时的官方文档为准（待验证）；尤其需要确认：Workflow 尚未执行到 `waitForEvent` 时收到的 `sendEvent` 是否会被缓存。上面的 `check-callback` / `recheck-callback` 保证即使不缓存也不会丢结果。

### 回调入口
`POST /api/webhooks/media/:provider?task=:id&sig=:hmac`
- 用自签 HMAC（taskId + secret）校验 URL，外加 provider 自身的签名校验（如有）。
- **先落库，再通知**：把解析后的结果写入 `ai_task.callback_payload`（仅当为空时写入，幂等），再 `env.AI_MEDIA_WORKFLOW.get(ai_task.workflow_instance_id).sendEvent({ type: 'media.done', payload })`。`sendEvent` 失败不影响返回 200——Workflow 会在 `check-callback` / 超时后的 `recheck-callback` 中读到结果。

### 前端
- 提交后立即返回 `taskId`；任务列表/详情页轮询 `GET /api/ai/tasks/:id`（指数退避，2s → 10s）。
- 后续可升级为 Durable Objects + WebSocket 实时推送。

### 并发与防滥用
- 并发数检查与创建任务、预扣必须在**同一事务**中，并先取空间级事务锁，否则两个同时到达的请求都能通过 count 检查：
  ```sql
  BEGIN;
  SELECT pg_advisory_xact_lock(hashtextextended('ws:' || $ws, 0));   -- 同一空间的提交串行化，事务结束自动释放
  SELECT count(*) FROM ai_task WHERE ws = $ws AND status IN ('queued','running');   -- 须 < maxConcurrentTasks
  INSERT INTO ai_task (...);   -- 含 pricing 快照、provider_request_key、deadline_at
  -- hold()：锁批次并预扣（同一事务）
  COMMIT;
  -- 事务提交后再启动 Workflow；启动失败则将任务标记 failed 并 release
  ```
  Advisory lock 是事务级的，在 Hyperdrive 的事务模式连接池下可用（待验证，列入 Phase 0）。
- `RL_AI` 限流绑定按 workspace + user 限制提交频率，用于防刷和削峰。
- 限流绑定按数据中心分别计数、不精确，**不能用来实现配额**：需要精确保证的限制（并发任务数、积分余额、每日额度等）一律在 Postgres 事务里检查。
- 可选内容审核：提交前对 prompt 做审核（服务商自带或单独调用）。

### 安全下载
`copyOutputsToR2` 只允许从该 provider 的已知域名下载（防 SSRF），限制最大文件大小与 MIME 类型。

## 5. 文件与输入素材

- 图生图 / 图生视频的输入，直传 R2 分三步：
  1. `POST /api/files/uploads`（声明 `mime`、`size`）：服务端校验 MIME 白名单、单文件上限、`已用 + size ≤ storageGb`，插入 `file(status='pending')`，返回预签名 PUT URL（有效期 10 分钟，签名包含 `Content-Type`）。
  2. 前端直传 R2。
  3. `POST /api/files/:id/complete`：服务端 `R2.head()` 取对象**真实**大小与类型，与声明不符或超出配额 → 删除对象、标记失败；通过则置 `status='ready'`。
  - 原因：R2 的预签名 PUT 无法限制上传体积（S3 的 POST policy `content-length-range` 在 R2 不可用），只能上传后校验。提交任务时只接受 `status='ready'` 的 `fileId`；Cron 清理超过 1 小时仍为 `pending` 的记录及对象。
  - 服务端给 provider 生成短期可读 URL。
- 产出文件访问：通过 `/api/files/:id` 鉴权后 302 到短期签名 URL；公开分享作为可选功能（`file.public_token`）。
- 预签名 URL 需要 R2 的 S3 兼容 API 凭证（`R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY`，令牌权限限定到 `FILES` 桶），用 `aws4fetch` 在 Worker 内签名。
- 配额：按 `sum(file.size) where status='ready' and deleted_at is null` 对照权益 `storageGb`。
