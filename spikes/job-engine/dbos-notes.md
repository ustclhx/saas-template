## Native functionality and exact API differences

Read the actual installed `dist/src/dbos.d.ts`, `step.d.ts`, `workflow.d.ts`, `wfqueue.d.ts`, `client.d.ts`, `dbos-executor.js`, and `system_database.js`.

- Native `DBOS.migrate(url, { applicationRole: 'app' })` grants the runtime DBOS schema permissions; `DBOS.setConfig({runMigrations:false})` verifies migration version and executes no runtime DDL. Actual source/docs: https://docs.dbos.dev/typescript/reference/dbos-class and https://docs.dbos.dev/typescript/reference/configuration .
- Native durable `DBOS.registerWorkflow`, `startWorkflow({workflowID,queueName})`, `runStep`, `sleep`, and `cancelWorkflow`. Native `recv(topic,{timeoutSeconds})` exists but is not used by the final adapter because its FIFO ordering cannot resolve same-millisecond ties through a public option. Native step retry uses **maxAttempts including initial attempt**, seconds for interval, numeric multiplier, `shouldRetry`, and `timeoutMS`; adapter maps contract retry limit+1, milliseconds/1000, `constant`=>1 / `exponential`=>2, name-based NonRetryableError exclusion. `linear` uses a workflow-level attempt loop: each attempt is a native step with retries disabled and maxAttempts=1, so its failure is checkpointed independently, followed by durable DBOS.sleep(delayMs * attempt). Per-attempt timeout remains native; replay reads cached failures and durable sleep deadlines before continuing. A name-based NonRetryableError exits this loop immediately. Native step attempt code is not forcibly stopped on timeout; late side effects remain a risk when callback does not observe DBOS cancellation/timeout signals.
- Native queue `registerQueue` is after launch and persists configuration. DBOS has native globalConcurrency and global rateLimit: https://docs.dbos.dev/typescript/reference/queues . They limit workflows rather than individual messages inside a batch, so this prototype uses explicit per-message quota supplementation instead.
- Native `getWorkflowStatus` has PENDING/ENQUEUED/DELAYED/SUCCESS/ERROR/CANCELLED/MAX_RECOVERY_ATTEMPTS_EXCEEDED. Supplemental phase table distinguishes waiting from running; native DBOS has no distinct waiting status.
- Launch automatically recovers the same executorID and version. Worker ID must remain stable across restart. No automatic detection/recovery of a dead differently named worker is added. Different executor/version failover needs supervised recovery/Conductor; it is not established by this implementation.

## Explicit supplementation

1. `spike.dbos_message` is a transactional inbox. `send(message, tx)` inserts into the caller's actual Drizzle transaction via executeInDrizzle(tx, text, values), retaining parameter binding; caller-supplied postgres.js transactions and the root driver remain supported. Commit/rollback therefore includes business writes. `sendBatch` uses one transaction. This avoids claiming native DBOS supports Drizzle/postgres.js transactional enqueue (the SDK's native transactional API accepts a `pg` client).
2. Poller groups eligible rows into actual arrays, maximum10 main/other and maximum2 limited, full batch immediately or oldest eligible row after5s. Batch ownership is persisted before publishing a stable batch workflow ID; both workers can republish safely through DBOS ID deduplication. Group claim uses advisory transaction locks and SKIP LOCKED. A DBOS durable step calls handler.batch once per attempt, with independent ack/retry closures, then persists each outcome. Successful members stay acked when failed members retry. QueueMessage.timestamp is a Date from the owned immutable sent_at column; retry scheduling updates created_at without changing sent_at. Explicit privileged migration backfills existing rows from created_at, sets a default and NOT NULL, and performs no runtime DDL. For historical rows already retried before this migration, the original send time cannot be reconstructed from the previous schema. Default missing ack retries. At attempt6 unacked messages enter supervisor's `spike.dead_letter`; default retries30,60,120,240,480 seconds (900 cap available), explicit callback delay honored.
3. `spike.dbos_quota` reserves at most2 simultaneous limited-message slots and at most3 starts over a sliding10s period under a shared PG advisory lock. Each limited batch contains<=2 messages so Promise.all handler starts all have slots. Permits are held through the batch completion; recovery reuses ownership. Admission may be conservative (a size2 batch waits when only1 rate token remains). Reservation precedes actual audit start by callback/DB latency; exact timestamp behavior is supervisor-tested. An unrecovered dead worker or terminal batch persistence error can leave active reservations; stale-permit fencing/reaping is not implemented or verified.
4. `spike.dbos_phase` records waiting around native durable sleeps and the supplemental durable event waiter. This requires two small durable steps per wait, rather than fabricating DBOS waiting state.
5. `sendEvent` read-locks `dbos.workflow_status` with SELECT FOR UPDATE, rejects missing/terminal instances atomically relative to native status transitions, and inserts **only the owned** `spike.dbos_event` inbox. Native DBOS `system_database.js` recv query orders only `created_at_epoch_ms ASC` with no tie breaker; two accepted same-millisecond messages therefore have no documented strict FIFO order. Updating native notification rows would violate design§7, so it was rejected and removed. The owned event inbox has a bigserial sequence, with sends for an instance serialized by its native status read-lock; no native system-table INSERT/UPDATE/DELETE is issued by adapter SQL.
6. `spike.dbos_wait` journals `(workflow_id,name)` with an absolute first-created deadline and a completed result. Within a transaction, the waiter locks its journal, consumes the earliest owned inbox event by sequence, and stores that exact result together. A DBOS.runStep surrounds the waiter; if the process dies after event consumption but before the DBOS step checkpoint, retry reads the saved event and never loses it. Timeout is also cached, and recovery reuses the persisted deadline. Eligible inbox events must have been received by that deadline, preventing a late arrival from winning after recovery. The adapter converts the persisted numeric timestamp to a Date after the native checkpoint/inbox read, including replay. Polling every100ms observes the native DBOS step cancellation signal. This adds two owned tables and DB polling to obtain strict FIFO, crash-safe consumption and deadline semantics; it is explicitly supplementation rather than native messaging evidence.

A callback/DBOS checkpoint crash gap remains at-least-once: business side effects need idempotency. Inbox outcome SQL and DBOS step checkpoint are separate transactions. The common crash effect uses an idempotent key to demonstrate this gap honestly; no exactly-once claim is made.

## Permission and validation

Migration: privileged local PG role needs schema/table/index creation, DBOS migrations, grants. Runtime app gets USAGE on spike/dbos, table DML, sequence USAGE/SELECT; no CREATE/ALTER. DBOS uses its own pg pool(max5); common handler and owned inbox/journal use postgres.js pool(max3). Runtime start creates no schema.

Quick executor validation: `node --check spikes/job-engine/dbos.mjs` => passed. Runtime smoke should use supervisor's worker harness after migrating with PGUSER=postgres, then launch worker with PGUSER=app. All connection configuration is derived from PG environment variables; never log URLs/passwords. No long scenario was started by this executor.
